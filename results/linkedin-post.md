# LinkedIn 게시글

10억 행으로 DB 성능을 비교해 봤는데, 자꾸 DuckDB에 눈이 갔습니다.

처음 baseline 결과를 봤을 때도 꽤 좋았습니다. 그런데 각 DB에 인덱스를 추가하거나 데이터 정렬을 적용한 optimized 결과에서도 여전히 준수하더라고요.

‘이 정도면 Python 데이터 처리에도 DuckDB를 먼저 써봐야 하는 것 아닐까?’라는 생각이 들었습니다.

이번에 비교한 DB는 ClickHouse, DuckDB, PostgreSQL, SQLite입니다. 같은 논리 데이터로 단건 조회, 날짜 필터 집계, 전체 집계, 조인을 각각 30회씩 실행했습니다. 큰 테이블은 10억 행, 조인할 테이블은 100만 행으로 구성했습니다.

결과를 보면서 기억에 남은 점은 다섯 가지입니다.

- **DuckDB는 여러 분석 쿼리에서 고르게 좋았습니다.** optimized 기준 날짜 필터 집계는 평균 85 ms, 전체 집계는 849 ms, 조인은 1.15초였습니다. 특히 다른 DB에도 최적화를 적용한 뒤에 이 정도 성능을 유지했다는 점이 인상적이었습니다.

- **집계에서는 ClickHouse가 빨랐습니다.** optimized 날짜 필터 집계는 평균 60 ms, 전체 집계는 549 ms로 가장 빨랐습니다. 기간별 지표를 반복해서 뽑는 작업이라면 ClickHouse를 먼저 살펴볼 것 같습니다.

- **PostgreSQL과 SQLite도 잘하는 일이 분명했습니다.** 인덱스를 추가한 단건 조회는 평균 0.187 ms, 0.051 ms였습니다. 큰 테이블을 집계할 때와 특정 한 행을 찾을 때의 결과가 이렇게 달랐습니다. 평소 어떤 쿼리를 많이 쓰는지가 DB 선택에 얼마나 중요한지 다시 느꼈습니다.

- **최적화의 효과는 생각보다 쿼리를 많이 탔습니다.** 날짜 필터 집계는 ClickHouse가 약 7.9배, DuckDB가 약 5.2배 빨라졌습니다. 반면 전체 집계와 조인은 개선이 작거나 오히려 느려진 경우도 있었습니다. DuckDB는 저장 공간도 약 두 배로 늘어, 자주 쓰는 쿼리에 이득이 있는지 함께 봐야겠더라고요.

- **표준편차를 같이 표시하니 평균만 볼 때 놓쳤던 게 보였습니다.** DuckDB 전체 집계의 평균은 884→849 ms로 줄었는데, 표준편차는 18→401 ms로 커졌습니다. 평균은 조금 빨라졌지만 실행 시간은 더 들쭉날쭉해진 셈입니다. 이번에 차트에 꼭 함께 넣고 싶었던 부분입니다.

지금이라면 Python에서 데이터를 변환하고 조인하는 작업에 DuckDB부터 적용해 보고 싶습니다. 집계 중심의 분석 서비스라면 ClickHouse를, 서비스의 트랜잭션 데이터라면 PostgreSQL을, 앱 안의 로컬 데이터라면 SQLite를 각각 검토하겠습니다.

물론 이번에는 합성 데이터를 단일 클라이언트로 조회했습니다. pandas와 직접 비교하거나 운영 환경의 동시 요청·쓰기를 테스트한 것은 아닙니다. SQLite optimized 조인은 첫 측정이 6시간을 넘겨 중단했고, 완료된 결과와의 비교에서 제외했습니다.

다음에는 실제 Python 파이프라인에서 데이터 읽기부터 변환, 결과를 가져오는 과정까지 비교해 보고 싶습니다. 쿼리가 빠른 만큼 전체 작업도 빨라지는지 궁금해졌습니다.
